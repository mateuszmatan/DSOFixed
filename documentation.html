DevSecOpsJenkinsLibrary

Jenkins Shared Library implementing the full DevSecOps pipeline: build, unit tests with coverage, Nexus IQ dependency scan with automatic GoldenFix pull requests, SonarQube, SAST and DAST with HCL AppScan, deployments, smoke / regression / performance tests, an HTML pipeline report and InfluxDB metrics.

Which pipeline to use

The library ships three entry points that share the same services, thresholds, release gate and report.

Entry pointRunsUse it when
devSecOpsPipelineAll thirteen stages in one buildOne job should cover the whole flow
devSecOpsSecurityPipelineUnit tests, Nexus IQ, SAST, SonarQube, snapshot delivery; archives config.yaml and the release gate verdictThe static part runs on every commit and the rest is a separate job
devSecOpsExtendedPipelineRD deployment, regression, smoke, performance, DAST, release delivery, QC deploymentDownstream of the security pipeline, named in securityPipeline:, inherits the verdict through the copied release-gate.json

After every build the library

  • generates an HTML pipeline report with the stage flow, vulnerability counts, policy status, SonarQube badges and coverage,
  • adds a Smoke tests table with one row per executed job and a link to each build,
  • adds a Nexus IQ GoldenFix card with the pull request link, the applied dependency upgrades and the fixes that could not be applied,
  • adds a Release policy card stating whether the artifact may be released to Nexus and deployed to QC,
  • archives the HTML reports, the DAST PDF report and the release gate verdict as build artifacts,
  • sends DORA metrics to InfluxDB when configured.

2 Application requirements

  • Git repository reachable from Jenkins with Jenkinsfile and config.yaml committed at the repository root.
  • Supported build tool: Gradle, Maven or Flutter. Wrapper scripts are preferred and must be executable.
  • The code must compile, because the SAST stage builds an IRX archive from a compile step.
  • Unit tests with coverage: JaCoCo for Gradle and Maven, lcov for Flutter. The required 60 % line coverage comes from resources/defaults.yaml and cannot be changed by a project. Below it the Unit tests stage turns orange, the build continues to RD and the Nexus release plus the QC deployment stay blocked.
  • HCL AppScan on Cloud application registered, with the application id and an API key pair in config.yaml.
  • SonarQube project registered with a unique project key and a badge token for the report.
  • Nexus IQ application registered, with build artifacts matching the configured scan patterns.
  • Bitbucket repository and credentials when GoldenFix pull requests should be raised, plus git on the agent.
  • Test jobs exist in Jenkins, or are referenced by full URL when they live on another Jenkins instance.
  • DAST target reachable from the agent when dast.enabled: true, or an AppScan Presence id for internal targets.

Build parameters

The library adds one boolean parameter. A policy violation never fails the pipeline: the stage turns orange, the build becomes UNSTABLE and keeps running, and the release plus QC stay blocked.

ParameterDefaultDescription
DEPLOY_HIGHER_ENVfalseDeploy to QC, allowed only when every earlier stage is green.
!
There is no override parameter and no project threshold. Every build runs every stage. A stage that breaks the library policy is coloured orange with the counts behind it, the snapshot delivery and the RD deployment still happen, and the Nexus release plus the QC deployment stay blocked until the findings are fixed.

8 Step 4 — First run

  • Stage 1 checks out the code and reads config.yaml. The console prints the library policy that every stage is checked against.
  • Stage 5 (SAST) uploads compiled code to ASoC and waits, typically 20 to 50 minutes.
  • Stage 11 (DAST) is skipped for projects with dast.enabled: false.
  • Stage 12 is skipped when any earlier stage is orange, and stage 13 runs only with DEPLOY_HIGHER_ENV=true and every stage green.
  • Open Pipeline Report in the left sidebar after the build.

10 Pipeline stages

Stage 2: Unit tests

Runs the tests with coverage collection and compares the line coverage with coverage.minLine of resources/defaults.yaml, which is 60 %. The stage never fails on coverage: below the required value the box turns orange, shows the measured value next to the required one, and the reason states that the step failed and that the Nexus release and the QC deployment are blocked. A missing coverage report is treated the same way.

Stage 3: Dependencies scan (Nexus IQ)

Runs nexusPolicyEvaluation and compares the critical, severe and moderate counts with the library thresholds. On a violation the stage turns orange with the counts, the GoldenFix remediation starts and the release plus QC are blocked, while the pipeline keeps running.

GoldenFix — automatic remediation pull request

  1. Reads the violating components from the Nexus IQ policy report and keeps only direct dependencies with a non waived violation at or above the configured threat level.
  2. Asks the Component Remediation API for the target version. The Golden Version (recommended-non-breaking-with-dependencies, Maven only) is preferred, followed by next-no-violations and the remaining remediation types.
  3. Searches the whole source tree, multi module projects included, and updates Maven pom.xml files with their properties, Gradle build files, gradle.properties and version catalogs, package.json files and pip requirement files.
  4. Commits in a separate git worktree, so the pipeline workspace is untouched, pushes the branch GoldenFix-YYYYMMDDHHMM and opens a Bitbucket pull request with the same name.
  5. All projects of one build share one pull request. The report states that the pull request was raised and links to it.

Lock files such as package-lock.json or poetry.lock are not regenerated, and hash pinned requirement files are left untouched. A GoldenFix error never changes the result of the Nexus IQ stage, it is only reported.

Stage 11: DAST — HCL AppScan

Runs for projects with dast.enabled: true. The report is downloaded as HTML, which is parsed for the vulnerability counts, and as PDF. Both are archived, and the Security Gates table offers three entries: the HTML report, the HCL AppScan console page of the scan and the PDF report. Above the DAST thresholds the stage turns orange with the critical, high and medium counts.

Stages 6 to 10: delivery and tests

Stage 6 publishes the snapshot artifact and stage 7 deploys to RD. Both always run, even when an earlier stage is orange. Then the tests run in the order regression, smoke, performance, followed by DAST. Each test stage needs at least one configured job. Every test stage runs all configured jobs, even when some fail, and then turns orange with a summary of the failed jobs. A stage may contain hundreds of jobs. At most tests.maxParallel jobs run at the same time, with a worker pool above that limit. Remote jobs can be given as a full URL without any Remote Jenkins configuration.

How a failure is reported: orange stages and the release gate

No security or test finding stops the pipeline. Every stage from the unit tests to DAST runs on every build. A stage that breaks the library policy is marked orange, the build becomes UNSTABLE, and the reason names the failed step, the counts behind it and the consequence.

StageOn a policy violationConsequence
Unit testsOrange, with the measured and the required line coverageRelease and QC blocked
Dependencies scan (Nexus IQ)Orange, with critical / high / medium counts, GoldenFix pull request raisedRelease and QC blocked
SASTOrange, with critical / high / medium countsRelease and QC blocked
SCA (SonarQube)Orange, with the quality gate statusRelease and QC blocked
Nexus delivery (snapshot)Always runs—
Lower test region deployment (RD)Always runs—
Regression, smoke, performanceOrange, with the failed jobsRelease and QC blocked
DASTOrange, with critical / high / medium countsRelease and QC blocked
Nexus delivery (release)Skipped when anything above is orangeNo release artifact

The release gate collects the verdict. It blocks the second Nexus delivery and the QC deployment when any stage is not green, when a scanner count exceeds the library policy, or when the line coverage is below the required 60 %. The report shows a Release policy card listing every violation, for example gui Dependencies (Nexus IQ) critical 1 > 0 or line coverage 41.0% below the required 60%.

Each pipeline judges the results it owns and hands its verdict to the next one through the archived release-gate.json, so an orange stage in the security pipeline also blocks the release in the extended pipeline.

14 Supported deployment targets

VM deployment over SSH (deployTarget: vm)

  1. Verifies SSH connectivity to the host of the environment.
  2. Creates the deploy directory, copies the deployment script and the version file with SCP.
  3. Executes the deployment script on the remote host.

OpenShift deployment (deployTarget: openshift)

  1. Reads cluster and credentials from deploy.openshift.<env>.
  2. Applies the process template, tags the image and restarts the rollout.

Both paths pass through the release gate for the QC environment.

15 Troubleshooting

Nexus release and QC deployment were skipped

The release gate blocked them because at least one earlier stage is orange. The Release policy card lists every violation, for example gui Dependencies (Nexus IQ) critical 1 > 0, stage 'Smoke tests' is WARN or line coverage 41.0% below the required 60%. The snapshot delivery and the RD deployment are never blocked.

A stage is orange and the build is UNSTABLE

That is the normal reaction to a policy violation or a failed test job. The stage box carries a Reason line with the failed step, the counts and the sentence that the Nexus release and the QC deployment stay blocked. The pipeline continues with every remaining stage.

GoldenFix pull request was not raised

The GoldenFix card shows the reason. NOT_CONFIGURED means scm.bitbucket.url or credentialsId is missing. NO_FIXES means Nexus IQ has no remediation version for the violating direct dependencies. NO_MANIFEST_CHANGES means the vulnerable versions are not declared in any supported manifest, for example because a BOM manages them. ERROR means the [GOLDENFIX] lines in the console hold the details, usually permissions or push rights.

DAST PDF report is missing

The DAST stage downloads the report as HTML and as PDF and archives both. If only the HTML link appears, look for [DAST] PDF report not found in the console; generating the PDF in ASoC may have taken longer than the download window.

Many smoke tests (hundreds of jobs)

All jobs run even when some fail, and at most tests.maxParallel run at the same time. Remote jobs can be listed by URL in tests.smoke.urls and share settings through tests.smoke.defaults. Raise maxParallel only if the remote instances have enough executors.

A test stage is orange with "no test jobs configured"

Each test stage needs at least one entry. A placeholder with an empty job is reported as NOT_CONFIGURED, which counts as a job that did not succeed, so the stage turns orange and the release and QC stay blocked.

"config.yaml not found in workspace"

The project repository must contain config.yaml at its root with a projects: section, committed on the built branch.

SAST stage takes very long or times out

The library default is 50 minutes of polling plus IRX generation. Only the library team can change it.

Nexus IQ shows 0 vulnerabilities but the build is unstable

The sandbox may have blocked direct access to the scan result object. The library falls back to parsing the console log; if that fails too the counts stay at zero while the plugin result is still respected.

SonarQube stage fails with "SonarQube server not configured"

Register the server in Manage Jenkins, Configure System, SonarQube servers under the name SonarQube.

16 SelfService — onboard a project step by step

Everything below is done by the project team, without any request to the DevSecOps team.

Step 1 — Check the prerequisites of your application

  • The repository is reachable by Jenkins and builds with Gradle, Maven or Flutter.
  • Unit tests produce a JaCoCo XML report, or coverage/lcov.info for Flutter, with at least 60 % line coverage.
  • The build produces a JAR or WAR under build/libs or target.
  • VM deployment: a deployment script, a version.properties with APP_VERSION= and SSH access from the agent to the RD and QC hosts.
  • OpenShift deployment: deployConfig.yml in the repository root and the cluster tokens in Jenkins credentials.

Step 2 — Register your application in the tools

ToolWhat you needWhere it goes in config.yaml

SonarQubeProject key, project name, badge tokentools.sonar.*
Nexus IQApplication public idtools.nexusIq.application
BitbucketRepository URL and credentials with push and pull request rightsscm.bitbucket.*
InfluxDB (optional)Write endpoint and tokeninflux.*

Step 3 — Create the test jobs

Create at least one Jenkins job for regression, one for smoke and one for performance tests. They may live on this Jenkins instance (type: local) or on any other instance, referenced by full URL. A stage may hold hundreds of jobs; at most tests.*.maxParallel run at the same time.

Step 4 — Add config.yaml to your repository root

Copy config.yaml.template from this library, keep only the projects: section and fill in your values. Do not add thresholds or a coverage minimum, they come from the library. A complete two project example with SAST, DAST, SonarQube, Nexus IQ, GoldenFix, smoke, regression, performance and both deployment targets is in examples/CertScanner/config.yaml.

Step 5 — Add the Jenkinsfile to your repository root

@Library('DevSecOpsJenkinsLibrary') _

devSecOpsPipeline(
    projectNames: 'gui,backend-api',
    agentNames:   ['linux-agent', 'windows-agent']
)

Use devSecOpsSecurityPipeline plus devSecOpsExtendedPipeline instead when the static part should run on every commit and the rest in a separate job. The extended job takes securityPipeline: '<name of the static job>' and copies config.yaml and release-gate.json from it; chain the two jobs in Jenkins, the library does not start the second one by itself. A complete example of both is in examples/README.md.

Step 6 — Create the Jenkins job

A Pipeline job with Pipeline script from SCM, your Git repository, your branch and the script path Jenkinsfile. Nothing else has to be configured.

Step 7 — Run the pipeline

Click Build Now. Select DEPLOY_HIGHER_ENV only when you want the QC deployment, which happens only when every stage is green.

Step 8 — Read the report

  • the stage flow with one box per stage and per project, green when the stage passed and orange when it broke the policy,
  • the Reason line of each orange box, with the counts and the consequence,
  • the Security Gates table with the findings of SAST, DAST, Nexus IQ and SonarQube and links to the reports, the HCL AppScan console and the PDF,
  • the Release policy card telling you whether the artifact was released and whether QC is allowed,
  • the Nexus IQ GoldenFix card with the pull request that upgrades the vulnerable dependencies,
  • the Smoke tests table with one row per job.

Step 9 — Fix what is orange

Merge the GoldenFix pull request, fix the SAST, SonarQube or DAST findings, raise the coverage or repair the failing test jobs. The next green build is released to Nexus and may be deployed to QC.

Onboarding checklist

  • Jenkinsfile and config.yaml committed at the repository root
  • appId, asoc.keyId and asoc.keySecret filled in for every project
  • SonarQube project key and Nexus IQ application configured
  • At least one job configured for regression, smoke and performance
  • scm.bitbucket.url and credentialsId set, so GoldenFix can raise pull requests
  • Deployment target configured, deploy.vm.* or deploy.openshift.*
  • Unit tests reach 60 % line coverage
  • First build green, report opened, release policy card checked
