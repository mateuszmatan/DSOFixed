DevSecOpsJenkinsLibrary

Jenkins Shared Library implementing the full DevSecOps pipeline: build, unit tests with coverage, Nexus IQ dependency scan with automatic GoldenFix pull requests, SonarQube, SAST and DAST with HCL AppScan, deployments, smoke / regression / performance tests, an HTML pipeline report and InfluxDB metrics.

Which pipeline to use

The library ships three entry points that share the same services, thresholds, release gate and report.

Entry pointRunsUse it when
devSecOpsPipelineAll thirteen stages in one buildOne job should cover the whole flow
devSecOpsSecurityPipelineUnit tests, Nexus IQ, SAST, SonarQube, snapshot delivery, then triggers the extended pipelineThe static part runs on every commit and the rest is a separate job
devSecOpsExtendedPipelineRD deployment, regression, smoke, performance, DAST, release delivery, QC deploymentDownstream of the security pipeline, inherits the release verdict through release-gate.json

After every build the library

  • generates an HTML pipeline report with the stage flow, vulnerability counts, policy status, SonarQube badges and coverage,
  • adds a Smoke tests table with one row per executed job and a link to each build,
  • adds a Nexus IQ GoldenFix card with the pull request link, the applied dependency upgrades and the fixes that could not be applied,
  • adds a Release policy card stating whether the artifact may be released to Nexus and deployed to QC,
  • archives the HTML reports, the DAST PDF report and the release gate verdict as build artifacts,
  • sends DORA metrics to InfluxDB when configured.

2 Application requirements

  • Git repository reachable from Jenkins with Jenkinsfile and config.yaml committed at the repository root.
  • Supported build tool: Gradle, Maven or Flutter. Wrapper scripts are preferred and must be executable.
  • The code must compile, because the SAST stage builds an IRX archive from a compile step.
  • Unit tests with coverage: JaCoCo for Gradle and Maven, lcov for Flutter. The library minimum is 60 % line coverage; a project may lower its own threshold, but below the library minimum the artifact is not released and QC is blocked.
  • HCL AppScan on Cloud application registered, with the application id and an API key pair in config.yaml.
  • SonarQube project registered with a unique project key and a badge token for the report.
  • Nexus IQ application registered, with build artifacts matching the configured scan patterns.
  • Bitbucket repository and credentials when GoldenFix pull requests should be raised, plus git on the agent.
  • Test jobs exist in Jenkins, or are referenced by full URL when they live on another Jenkins instance.
  • DAST target reachable from the agent when dast.enabled: true, or an AppScan Presence id for internal targets.

Build parameters

The library adds one boolean parameter. Security violations always fail the pipeline; a project that needs more room raises its own thresholds in config.yaml.

ParameterDefaultDescription
DEPLOY_HIGHER_ENVfalseDeploy to QC after all tests pass, allowed only when the library security policy is met.
!
OVERRIDE_BBH_POLICIES no longer exists. Raise the project thresholds in config.yaml instead. The build then keeps running and reaches RD, while the Nexus release and the QC deployment stay blocked until the library policy is met.

8 Step 4 — First run

  • Stage 1 checks out the code and reads config.yaml. The console prints the effective thresholds and, when they were raised, the library policy next to them.
  • Stage 5 (SAST) uploads compiled code to ASoC and waits, typically 20 to 50 minutes.
  • Stage 11 (DAST) is skipped for projects with dast.enabled: false.
  • Stage 13 runs only with DEPLOY_HIGHER_ENV=true and a clean release gate.
  • Open Pipeline Report in the left sidebar after the build.

10 Pipeline stages

Stage 2: Unit tests

Runs the tests with coverage collection and compares the line coverage with coverage.minLine of the project. Below the project threshold the pipeline fails. Above the project threshold but below the library minimum the pipeline continues to RD, while the Nexus release and the QC deployment are blocked.

Stage 3: Dependencies scan (Nexus IQ)

Runs nexusPolicyEvaluation and compares the critical, severe and moderate counts with the effective thresholds. On a violation the stage fails and the GoldenFix remediation starts.

GoldenFix — automatic remediation pull request

  1. Reads the violating components from the Nexus IQ policy report and keeps only direct dependencies with a non waived violation at or above the configured threat level.
  2. Asks the Component Remediation API for the target version. The Golden Version (recommended-non-breaking-with-dependencies, Maven only) is preferred, followed by next-no-violations and the remaining remediation types.
  3. Searches the whole source tree, multi module projects included, and updates Maven pom.xml files with their properties, Gradle build files, gradle.properties and version catalogs, package.json files and pip requirement files.
  4. Commits in a separate git worktree, so the pipeline workspace is untouched, pushes the branch GoldenFix-YYYYMMDDHHMM and opens a Bitbucket pull request with the same name.
  5. All projects of one build share one pull request. The report states that the pull request was raised and links to it.

Lock files such as package-lock.json or poetry.lock are not regenerated, and hash pinned requirement files are left untouched. A GoldenFix error never changes the result of the Nexus IQ stage, it is only reported.

Stage 11: DAST — HCL AppScan

Runs for projects with dast.enabled: true. The report is downloaded as HTML, which is parsed for the vulnerability counts, and as PDF. Both are archived and linked from the pipeline report, exactly like the SAST report.

Stages 6 to 10: delivery and tests

Stage 6 publishes the snapshot artifact, stage 7 deploys to RD, then the tests run in the order regression, smoke, performance, followed by DAST. Each test stage needs at least one configured job. Every test stage runs all configured jobs, even when some fail, and reports one aggregated failure at the end. A stage may contain hundreds of jobs. At most tests.maxParallel jobs run at the same time, with a worker pool above that limit. Remote jobs can be given as a full URL without any Remote Jenkins configuration.

Project thresholds and the release gate

Project thresholds in config.yaml decide whether the pipeline keeps running. They may be raised for SAST, SCA, Nexus IQ and coverage only. Exceeding them fails the stage and the pipeline.

The library policy in resources/defaults.yaml decides what may leave the pipeline. When the findings or the coverage are worse than the library policy:

  • the artifact is not published to Nexus, neither the snapshot nor the release delivery,
  • the QC deployment is blocked,
  • the RD deployment still runs, so developers can work with the build,
  • the build is marked UNSTABLE, the blocked stage is shown as BLOCKED and the report shows a Release policy card with every violation.

Any stage that did not pass blocks the release too. If regression, smoke, performance or DAST fails in the extended pipeline, the artifact is not published to the release repository and QC stays unavailable.

Each pipeline judges the results it owns and hands its verdict to the next one through the archived release-gate.json, so a violation found in the security pipeline also blocks the release in the extended pipeline.

14 Supported deployment targets

VM deployment over SSH (deployTarget: vm)

  1. Verifies SSH connectivity to the host of the environment.
  2. Creates the deploy directory, copies the deployment script and the version file with SCP.
  3. Executes the deployment script on the remote host.

OpenShift deployment (deployTarget: openshift)

  1. Reads cluster and credentials from deploy.openshift.<env>.
  2. Applies the process template, tags the image and restarts the rollout.

Both paths pass through the release gate for the QC environment.

15 Troubleshooting

Nexus delivery and QC deployment were skipped

The release gate compares the scan results and the line coverage with the library policy in resources/defaults.yaml. A project may raise its own thresholds for SAST, SCA, Nexus IQ and coverage in config.yaml, which lets the build reach RD, but while the library policy is exceeded the artifact is not published to Nexus and QC is blocked. The build becomes UNSTABLE and the Release policy card lists every violation.

GoldenFix pull request was not raised

The GoldenFix card shows the reason. NOT_CONFIGURED means scm.bitbucket.url or credentialsId is missing. NO_FIXES means Nexus IQ has no remediation version for the violating direct dependencies. NO_MANIFEST_CHANGES means the vulnerable versions are not declared in any supported manifest, for example because a BOM manages them. ERROR means the [GOLDENFIX] lines in the console hold the details, usually permissions or push rights.

DAST PDF report is missing

The DAST stage downloads the report as HTML and as PDF and archives both. If only the HTML link appears, look for [DAST] PDF report not found in the console; generating the PDF in ASoC may have taken longer than the download window.

Many smoke tests (hundreds of jobs)

All jobs run even when some fail, and at most tests.maxParallel run at the same time. Remote jobs can be listed by URL in tests.smoke.urls and share settings through tests.smoke.defaults. Raise maxParallel only if the remote instances have enough executors.

"No test jobs configured — tests are mandatory"

Each test stage needs at least one entry. A placeholder with an empty job is reported as NOT_CONFIGURED, which still counts as a failed job for the stage result.

"config.yaml not found in workspace"

The project repository must contain config.yaml at its root with a projects: section, committed on the built branch.

SAST stage takes very long or times out

The library default is 50 minutes of polling plus IRX generation. Only the library team can change it.

Nexus IQ shows 0 vulnerabilities but the build is unstable

The sandbox may have blocked direct access to the scan result object. The library falls back to parsing the console log; if that fails too the counts stay at zero while the plugin result is still respected.

SonarQube stage fails with "SonarQube server not configured"

Register the server in Manage Jenkins, Configure System, SonarQube servers under the name SonarQube.
